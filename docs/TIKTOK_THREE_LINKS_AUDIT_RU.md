Канонический домен всех трёх — `https://www.tiktok.com`, тип `/video/`,
не фотогалерея. yt-dlp может добавлять завершающий перевод строки к подписи;
это объясняет разницу длины описания с oEmbed на один символ.

Production-копия воспроизводимо завершает все три случая
`media_worker_reason=format_unavailable`: селектор допускает `mp4a.*`,
но отвергает `acodec=aac`. Исправление уже есть в main. В журнале рабочей
службы также обнаружены 13 таких ошибок; старые строки не содержат ID
публикации, поэтому приписывать каждую конкретной ссылке нельзя.

При первых сравнениях main и PR подготовили 2/3 видео (66,7%); при повторе
успешно загружены все три (100% этой выборки). Изменения PR #14 относительно
main не дали дополнительного исправленного случая: 0/3. Все три файла
прошли реальный `inspect_mp4`, ffprobe и декодирование первых трёх видеокадров
FFmpeg с кодом 0. Полное декодирование всей продолжительности и воспроизведение
в Discord не проверялись. Подтверждённое наличие AAC не заменяет прослушивание.

Пиковый измеренный RSS worker в заключительном прогоне: 67 997 696,
66 662 400 и 68 571 136 байт соответственно. Ограничения RAM, диска, CPU и
времени не срабатывали; ошибок DNS в этих прогонах не было. Первый HTTP 403
остаётся признаком зависимости от доступности TikTok; циклических повторов,
новых провайдеров, cookies и ослабления allowlist не добавлено.

## Источник сообщения DeepL и исправление

На реальном `https://x.com/maruzenskyy/status/2120886007512133929`
API FxTwitter вернул `code=200`, `translation.target_lang=ru`,
`translation.provider=deepl`, но в `translation.text` находилось многоязычное
уведомление `You're using an older version of DeepL.` вместо перевода
оригинального `kimi no aiba ga!`. Это ошибка upstream-поля, а не необходимость
устанавливать или обновлять DeepL на VPS: бот не вызывает DeepL напрямую.

В `social_posts.py` этот конкретный служебный ответ отклоняется до публикации
и до признания перевода успешным. Сохраняются исходный текст и существующий
fallback MyMemory. Если fallback недоступен, `translation_unavailable=True`
по-прежнему запрещает удаление исходного сообщения. Текст ошибок не пишется
в журнал: только `translation_rejected provider=... reason=deepl_upgrade_notice`.
Оригинальные посты о DeepL не фильтруются. Поздний live-запрос того же API
уже вернул обычный перевод от `grok`; фильтрация исходного ошибочного ответа
проверена регрессионными тестами на его зафиксированном тексте.

## Проверки и границы приёмки

100 unittest, Ruff 0.15.1, compileall и runtime imports проверяются локально
на Windows Python 3.13 и в изолированном окружении VPS Python 3.12.
Тесты содержат обезличенные свойства реальных форматов для всех трёх ссылок,
раскрытие redirect, лимит 19 МиБ, X-парсер, фотогалереи, перевод, Webhook receipt
и запрет удаления при неполной пересылке. Discord HTTP в тестах подменён.
CI на GitHub проверяет Python 3.13/3.14; окончательный статус указан в PR.

Фактическая отправка, плеер и звук в Discord ещё требуют проверки в приватном
канале с отдельным тестовым ботом. Также проверить X/GIF, фотогалерею, пост
с дополнительным пользовательским текстом, сохранение исходника при ошибке
перевода/загрузки и отсутствие повторного Webhook после неоднозначного ответа.
Наблюдавшееся `media_complete=False` и недоступный перевод хештегов не считаются
основанием ослабить удаление: при них исходник остаётся.

перезапуск production и изменения FunPayFlow в рамках диагностики не выполнялись.
