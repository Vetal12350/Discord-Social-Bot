## Результат аудита кода

- yt-dlp 2026.10.26 совпадает с последним stable release официального репозитория
  на момент проверки: https://github.com/yt-dlp/yt-dlp/releases/tag/2026.10.26 .
  Оснований слепо обновлять зависимости нет. Публичные TikTok endpoints всё равно нестабильны.
- Short redirects ограничены first-party HTTPS. Worker заново использует HEAD
  для short URL; лишний запрос — возможная поверхность отказа, но его вина
  в данном 403 не доказана. Перестройка этой ветви в этот PR не включена.
- MP4 selector уже принимает h264/aac и avc1/mp4a, предпочитает звук,
  отбрасывает известные oversized и HLS/DASH/H.265. Неизвестный размер остаётся
  риском, ограниченным фактическими байтами/временем. Без H.264 fallback может не быть.
- RSS 96 МиБ, CPU 8 с, worker wall 90 с download/25 с metadata, disk cap,
  общий timeout пересылки 180 с, один heavy worker и bounded cache сохраняются.
  Наблюдавшиеся видео укладываются; данных за повышение лимитов нет.
- Cache метаданных может держать устаревший signed URL; cache файлов ограничен
  24 МиБ/4 файлами/120 с. Истечение signed URL в конкретном production-403
  не доказано. Обновление метаданных без доказательств не добавлено.
- Допускаются 8 активных сообщений глобально и 4 на пользователя; metadata=2,
  heavy worker=1, media_lock сериализует подготовку/отправку. Пятая одновременная
  ссылка пользователя отклоняется, что подтверждено тестом. В production
  такого события не было. Ограниченная очередь с TTL/backpressure — отдельное
  будущее изменение после измерений; простое увеличение лимитов небезопасно.
- Webhook выполняет один POST и требует receipt с теми же файлами/текстом.
  Неоднозначный ответ не повторяется. Original/translation/media guards и
  keep_all не ослаблены. HTTP 404 пропавшего слайда исправить повтором нельзя.

## Исправление в этом PR

Раньше у TikTok worker не было даже одного безопасного повтора открытия HTTP
ответа. Теперь разрешён максимум один повтор GET/HEAD **на весь worker**:

- Только до возврата body: 429 и 500/502/503/504; 403 — только CDN-ответ,
  не first-party TikTok и не HTML. Login/CAPTCHA, Authorization, POST,
  404/410, ошибки policy/DNS/неизвестного transport и ошибки чтения body не повторяются.
- Те же URL/метод/заголовки, те же allowlist, public DNS, pinning и redirects;
  нет смены IP, cookies пользователя, прокси или новых провайдеров.
- Задержка 1 с либо Retry-After до 2 с. Длинный/невалидный Retry-After
  означает отказ от повтора, а не обрезание ожидания вопреки серверу.
- Повтор внутри того же процесса: прежний суммарный CPU/RSS/wall/disk budget
  автоматически охватывает обе попытки. Второго worker или FFmpeg нет.
- Безопасный retry marker доступен в parent journal и на успехе, и на отказе.
  Отдельно логируется HTTP status image/mp4 download без URL и body.
- X/Twitter не использует retry-класс. Webhook POST и удаление не менялись.

В изоляции искусственно возвращён первый HTTP 503 **перед** CDN body,
затем выполнен реальный GET TikTok: MP4 730856 байт, H.264/AAC; RSS 66379776,
CPU 2,82 с; delay=250 мс по Retry-After=0. Это проверка отказоустойчивого
пути с настоящим файлом, но искусственным первым отказом. Естественный
production-403 не воспроизведён и не объявлен исправленным.

121 unittest, Ruff и compileall проверены на Windows и в изолированном
Linux окружении; imports и pip check дополнительно проверены в Linux.
Отсутствие полученной подписи не доказывает, что оригинальный пост не имеет текста.
Тесты включают форматы/звук/размеры,
CPU/RSS/disk/wall guards, четыре быстрых сообщения, перевод, X, галереи,
Webhook errors/receipts, сохранение исходников, один retry на все URL,
Retry-After, запрет повторов challenge/POST/policy/body и отсутствие секретов.
